# 知识沉淀系统理念报告（人读版）

> 这份报告提炼 StaffDeck 知识库模块背后的**想法、取舍与设计哲学**，供你规划自己的知识沉淀系统时参考。
> 不涉及代码细节（那些在同目录的 AI 版报告里），只讲"为什么这么做"。

---

## 一、一个反直觉的核心决定：不用向量检索

看到"知识库"三个字，绝大多数人的第一反应是：embedding + 向量数据库 + RAG。StaffDeck 偏不。

它选择了另一条路：**让大模型沿着文档的结构导航，像人翻书一样找答案**，而不是把文本压成向量做相似度匹配。

为什么？三个理由：

1. **可解释性**。向量检索命中了一个段落，你只能说"相似度高"。而结构化检索的每一步——为什么选这篇文档、为什么选这个章节、这个段落凭什么进答案——都有明确的打分和理由，可以逐条审计。对企业知识库来说，"答案从哪来"和"答案是什么"同样重要。
2. **可溯源性**。每个证据块都带着完整的出处链：`文件名 / 章节路径 / 证据序号`。回答里的每个引用都能点回原文位置。向量化的知识是"死"的，你找不回它在原文里的上下文。
3. **零基础设施**。SQLite 就能跑，不用维护向量库、不用选 embedding 模型、不用管 embedding 模型升级后的全量重建。

代价也很诚实：同义词、改写的召回会变弱；每次检索要多花两次大模型调用（选文档、选章节）；文档量到千级以后预筛会吃力。StaffDeck 的答案是：用大模型路由来弥补语义召回的不足，并保留日后加 embedding 做"粗筛"的升级空间——因为**知识以什么形态沉淀，和用什么技术检索，是两件被刻意解耦的事**。

## 二、知识的载体：不是文本块，而是一座 Wiki

传统 RAG 把文档切成一堆孤立的片段丢进库里。StaffDeck 把每篇文档变成一座**小型 Wiki**（自定的 OKF 格式）：

- 每个文档有入口页、章节页、主题页、规则页，页与页之间有链接
- 每页都是"YAML 头 + Markdown 正文"——**人和机器都能直接读**
- 整座 Wiki 可以打包导出成 zip、可以再导入、可以做健康检查（lint：断链、孤儿页、缺引用、重标题）

这个选择的深意在于：**知识沉淀的产物应该是一种"资产"，而不是某个检索系统的中间态**。Wiki 形态的知识可以被人工编辑、被版本管理、被 lint 出质量问题、被迁移到任何其他系统。如果哪天换掉整个检索引擎，知识本身原封不动。

 lint 发现的 Wiki 质量问题（断链、孤儿页）会自动转成"待审核建议"，汇入人工审核队列——质量治理和知识发现用的是同一条流水线。

## 三、检索的思路：分层路由，而不是一锤定音

检索被设计成一条"逐步收窄"的漏斗：

```
概念（Wiki 页）→ 文档 → 主题桶 → 章节 → 证据块
```

每一层先用便宜的词法打分（专门处理中文：去口语噪声词、中文 n-gram 滑窗）筛出候选，再把候选交给大模型做精选。大模型只负责"选"，不负责"答"——选哪几篇文档、选哪几个主题，然后系统把对应原文取出来。

几个值得借鉴的细节：

- **每层都有回退**：大模型挂了、输出不合规，就退回纯词法打分的结果。系统永远能给出答案，只是可能没那么聪明。
- **大模型输出必须过白名单**：模型选的文档 ID、桶 ID 都要在候选清单里核验——防止模型幻觉出不存在的内容。
- **证据块之间是有"链"的**：同一个连续段落切出来的块互相记录前后邻居。命中一块，可以把前后文一起带出来（有上限），避免答案断章取义。
- **多样性保护**：选中 N 个主题桶时，每个桶至少保底一块证据，防止一个高分桶把配额吃光。

## 四、沉淀的闭环：机器发现，人来把关

这是整个系统最值得抄的部分。知识不是入库就结束了——入库的最后一步，系统会让大模型**重新读一遍刚入库的内容，主动发现"可执行的知识"**：

- 文档里描述了一个业务流程？→ 自动起草一份 **SOP 技能卡片**（带完整的流程图结构）
- 文档里写了接口信息？→ 自动起草一个**工具定义**
- 发现文档本身有矛盾或缺失？→ 记一条 **warning**

但这些草稿**绝不会自动生效**。它们进入一个待审核队列，经过严格的机器校验（字段白名单、流程图必须从起点可达所有节点、所有节点必须能到达终点），最后由**人点"确认"**才真正变成系统里的技能和工具；点"拒绝"就归档。

这条链路回答了一个知识系统最难的问题：**怎么让知识"活"起来变成行动，又不失控？** 答案是——机器负责发现的勤奋，人负责决策的审慎。

## 五、进化的机制：版本、分支、记忆、反馈

知识库不是一锤子买卖，它被当成代码一样管理：

- **版本化**：知识库有 semver 版本（1.0.0 → 1.1.0），可以回滚
- **分支**：每个智能体（或业务方）持有知识库的一个"分支"——可以在自己的分支上改，改好了"提升"回主干，改乱了"同步"回主干放弃本地修改。提升操作只是**把数据指针重新挂到新版本**，不复制数据，廉价且安全
- **删除也是温柔的**：普通用户"删除"知识库只是把自己的分支标记隐藏，数据还在；只有管理员才能物理删除

在此之外还有三条持续积累的暗线：

1. **记忆**：每轮对话结束后，异步地让大模型抽取值得记住的用户信息（身份、称呼、长期偏好），按 key 覆盖式更新。明确的原则是**只存稳定的东西，不存业务流水**——记忆宁缺毋滥。
2. **反馈分析**：用户点的每个踩，都会异步触发一次归因分析（是模型问题？技能问题？工具问题？还是用户没说清楚？），聚合成"当前点踩主要集中在某处"的看板。但 StaffDeck 在这里留了半个缺口——分析出的改进建议只是展示给人看，没有自动转回草稿队列。**你自己的系统可以把这半环补上**，让"用户反馈 → 改进草稿 → 人工确认"成为完整闭环。
3. **团队黑板**：多智能体协作时，成员可以把发现写到共享黑板上。黑板的去重策略很聪明：新内容是旧条目的子串就跳过（已有更完整的），旧条目是新内容的子串就合并升级（新内容更完整）。黑板上的高价值条目，可以再升级走完整的入库流水线，正式沉淀进知识库。

## 六、可以带走的设计原则

如果只用一页纸记住这套系统，记住这七条：

1. **沉淀物与检索技术解耦**。知识以结构化 Wiki 形态存在，换检索引擎不伤筋动骨。
2. **每条知识都有出处**。证据必须能指回原文的精确位置，引用编号可以审计。
3. **大模型做选择，规则做兜底**。每层 LLM 调用都有确定性回退；模型输出永远过校验和白名单。
4. **机器发现，人工生效**。任何自动产生的知识改进（SOP 草稿、工具草案、lint 警告）都先进审核队列，人确认才生效。
5. **知识像代码一样管理**。版本、分支、回滚、lint、导入导出，一个不少。
6. **积累要克制**。记忆只存稳定信息；黑板靠子串/超集关系自我合并；宁缺毋滥。
7. **诚实面对取舍**。不用向量库换来了简单和可解释，代价是语义召回——明确这个边界，并留好升级路径。
